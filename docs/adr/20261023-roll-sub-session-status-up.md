# Roll a session's sub session status up to every parent, from the transcripts, with no model calls

- Status: Accepted, amended 2026-10-27 and 2026-10-28
- Deciders: Eli
- Date: 2026-10-23
- Tags: sessions, sub-sessions, nesting, groups, side-panel, summaries, tools, permissions

## Context and Problem Statement

A session can have sessions nested under it, to any depth: side chats, forks, and sessions started from a chip. The owner runs many of them at once. To learn how a family is going he opens each session in turn. A session three levels down that waits for his approval is invisible from the top, and a folded family in the sidebar shows nothing of what is under it. A group already has a status panel for its sessions, but an ordinary chat that fans work out has none.

He asked for the status of the sessions below a chat to roll up into that chat: what each one last said, what needs him, and the same at every level. He also wanted the chat's own model to see the sessions below it. What does the status say, where does it come from, what does it cost, and how does it reach the page and the model?

## Decision Drivers

- Reading status must cost no tokens. The model never polls, and no model is asked to summarise.
- Status has to show where the owner already looks: the chat's header and side panel, the group's chat and the sidebar.
- A session must see only the sessions below it, at any depth, and never a sibling, a parent or another family.
- A message from a sub session is information and never permission. Passing status up must not start a turn in a parent by itself, because a turn can act.
- The page is read from disk on every request, so the new UI goes live before the server restarts. It has to work, as before, against the old server.
- A group's chat has one way to show status, and an ordinary chat should have the same one.
- Fetch only what is drawn. A family of 100 sessions must not cost 100 reads on every refresh.
- No new dependencies and no build step ([Node's standard library and plain browser files](20261007-no-dependencies-no-build-step.md), [Preact with htm](20261015-preact-htm-front-end.md)).

## Considered Options

1. Read each session's latest reply from its transcript when asked, and roll the counts up in the page and in the tools
2. Ask a model to summarise each session
3. Have each sub session send its status to its parent as a message

## Decision Outcome

Chosen option: "Read each session's latest reply from its transcript when asked, and roll the counts up in the page and in the tools", because it costs a file read and nothing else, never starts a turn, and gives the page and the model the same facts.

- **Summaries.** `lib/summaries.mjs` reads a session's transcript backwards from its last whole line, in chunks that double, and takes the newest assistant message with text. It reads no more than 2 MB in all and never reads a byte twice, so a last line longer than that ends the search, and the session reads as one that has said nothing. It gives `line`, the first sentence of that reply as plain text with code blocks skipped, cut to 160 characters, `ask`, the question or offer the reply ends on, found the same way and cut the same, or empty when it ends on neither, `reply`, the reply cut to 4,000 characters, and `at`, when it was said or null. A session that has said nothing has empty text and a null `at`. No model is called. A summary is kept per session until the transcript's size or modified time changes, and the 500 newest are kept. The transcript index can be seconds behind, so the file itself is asked.
- **Route.** `GET api/summaries?ids=a,b,c` is behind the same sign-in as the other routes. It answers `{ summaries: { <id>: { line, ask, at, pending } } }`, and each answer also has `reply` with `detail=1`. It takes 1 to 60 distinct ids. Blank ids are dropped, none is a 400 ("Name the sessions in ids."), and more than 60 is a 400 ("Ask for at most 60 sessions at a time."). An id that is no session, or is a group's chat, is left out with no word, so the answer tells nothing about it. An archived session is answered. `pending` is what the session waits on, from the live chat in the server's memory: each is the tool's name and a one-line summary of what it would do, cut to 80 and 200 characters. It carries no request id, input or rule, and is empty when the server has no chat for the session.
- **Flag.** `GET api/sessions` carries `features.subStatus`. A server that started before this change cannot send it, and the page treats the feature as absent.
- **Rules.** `public/ui/sub-rules.js` works from the flat list of rows, where a row's `via` names the nearest session it shows under. It finds every session below one at any depth, orders lines (needs the owner first, then working, recent and idle, the newest first, by the most urgent session in a line and under it), and rolls up the sessions below a session: the total, how many wait on the owner, how many work, and the most urgent mark. Archived sessions are left out of the counts. A session waits on the owner when its state is waiting or its mark is awaiting, and the lines, the sections, the roll-ups, the header button and a folded family all count it that way. The rows the tools read carry no mark, so the tools count by state alone. The roll-up line reads "3 sub sessions, 2 waiting on you, 1 working". The page and the tools import this one file, so they count the same way, and node tests it with no page.
- **Amended 2026-10-26, pull requests.** A card shows one line for its session's main pull request, under the reply and above its roll-up, saying what the owner has to do about it or who the session waits on, and a session whose line tells the owner to act shows the "Waiting on you" pill and counts as waiting. The page overlays the awaiting mark on its own copy of the rows (`withPulls` in `public/ui/sub-panel-rules.js`), so the lines, the sections, the summary line, the header button and its mark, and a folded family count it with no new rule. `lib/subs.mjs`, the two tools, the sidebar's marks and the group header are unchanged and count by state alone, so their counts can differ from the tab's. The status comes from a route of its own, `GET api/pulls`, and is decided in [Show pull request status on session cards](20261026-show-pull-request-status-on-session-cards.md).
- **Amended 2026-10-26, archive from a card.** Each card has an Archive button beside Details, so the owner can clear a session from the tab without the sidebar. It uses the sidebar's route and rules: an idle session is archived at once with an Undo note, a running one or one the server says is running asks first and then stops and archives it, and a refusal shows as a problem note with the card kept. The page's `archive` callback reaches the tab through `sessionActions` in `public/ui/subs.js`, beside `sessionIndex`, and `public/ui/close.js` holds the shared question text and the steps. The server is unchanged, so the sessions under an archived one still move up to the one it showed under. Only one archive request goes at a time, and a repeated Enter or Space or a second click of a double click does nothing. When a card goes, the focus moves to the title link of a session that was under it, else of the next card, else of the one before, else the line at the top of the tab, else the tab, else the message box, and never to an Archive button, so one more press cannot archive the next card.
- **Amended 2026-10-28, the next step in place of the first sentence.** The owner asked for each card to say what he should do next rather than how the session's reply began. A card's line under its pill is now one short imperative, decided by the first rule that fits: a pending approval reads "Approve Bash: npm test", with "(and 2 more)" for more than one, and a pending question "Answer its question: <the question>". A session that waits with nothing pending reads "Open it, it's waiting on you". One that ended on an error reads "Look at the error it stopped on". A main pull request that asks something of the owner reads as its action line from `statusOf` in `public/ui/pull-rules.js`, such as "Review the pull request", and the card then shows only the pull request's link under it, so the action is not said twice. A session Desktop marks as awaiting has no live chat here, so it reads as its reply's question or offer (below) when there is one, and "Open it, it's waiting on you" when not. A working session reads "Nothing yet, it's working". An idle session whose reply ends on a question reads "Answer its question: <the question>", and one that ends on an offer ("want me to", "shall I", "let me know" and the like) reads "Reply to its offer: <the offer>". The rest read "Nothing for now" with an open pull request and "Nothing, it's done" without one. The question or offer is the server's new `ask`, the last sentence of the reply's last three lines of prose that ends in a question mark or carries an offer. The rules are `nextStep` in `public/ui/sub-panel-rules.js`, and node tests them. A server that started before this change sends no `ask`, so an idle card there shows the first sentence as before. The tools, the group's ranked update and the summary line keep the first sentence, and Details still shows the whole reply.
  - **Options.** Three were weighed. The step can come from rules over what is already read: what is pending and the pull request's state come from the server with no model, and many replies end on a question or an offer that a rule can find. A model could write the step after each finished turn and keep it until the next. Or the chat's own model could be asked. The third starts a turn in the parent, which the decision drivers rule out.
  - **Cost of a model.** A step from Haiku 5.5, run as the session titles are ([Name sessions from their first turn](20261027-name-sessions-from-their-first-turn.md)), would read about 700 tokens of fixed framing, about 1,000 tokens of reply (the 4,000 characters `reply` keeps) and about 200 of facts and instructions, so about 1,900 input tokens and 20 output tokens a turn. The busiest day in the development Mac's transcripts, 2026-10-23, started 753 turns across every session, which bounds a busy tree from above. That is about 1.4 million input tokens and 15,000 output tokens a day, near 0.0004 dollars a call and 0.30 dollars a day if the title call's measured cost of 0.00015 dollars for 701 tokens scales with length, which was not measured. The money is small. A model also adds a process and seconds of delay to every finished turn, keeps a second copy of state that can go stale, and reads a transcript that can steer it.
  - **Chosen.** Rules, because they cost a file read and nothing else, they are right at once for the cases that need the owner (an approval, a question, a pull request), and the cost driver at the top of this record still holds. A model stays the fallback if the rules read badly in use.
- **Tools.** Every ordinary chat is given `list_sub_sessions`, `read_sub_session` and `send_session` by the `capcom` server (`lib/subs.mjs`, listed to a chat that is no group's). `list_sub_sessions` lists the sessions below the chat as a tree, up to 200 (100 by default), the ones that need the owner first, each with its roll-up and the first sentence of its latest reply. It lists archived sessions only with `include_archived`. `read_sub_session` reads the end of one session below the chat, at any depth and archived ones included: its last messages and tool calls, up to 60 items (20 by default), and what it waits on. Any id that is not below the chat, whether a sibling, a parent, another family's session or no session, gets the same one-sentence refusal, so the answer tells nothing about it. Each call looks the list up again. A group's chat keeps its own three tools and gets none of these.
- **Reads need no card.** The two read tools only read, so the runner allows them with no card, in every mode, for an ordinary chat alone. The CLI's own tools and `start_group_session` keep their cards, and no sub session tool can approve, deny, stop or archive anything. Only `send_session` can start a turn, and it always asks.
- **No turn in a parent.** Nothing pushes status up. A parent learns what is below it when the owner opens the tab, or when the model calls a tool, and a sub session's reply is read as information and never as a message the parent must act on. A turn starts in a parent only when the owner approves another chat's `send_session` card.
- **Amended 2026-10-27, send to any session.** `send_session(session_id, message)` lets an ordinary chat start or queue a turn in any other session on the Mac, a sub session or not, and never itself. A turn can act, so it asks with a card every time, in every mode including Bypass and Auto, with no Always allow (an ask rule in `lib/runner.mjs`, as a group's tools have). `SUB_READ_NAMES` in `lib/tools.mjs` holds the two reads and `SEND_NAME` the send. A chat has no tool that lists sessions outside its family, so the id has to come from the owner or from the text it works on, and an id that is no session is refused. The reads keep reaching sub sessions alone. The receiver sees a `<session-message>` turn from the sender, titled "(your parent session)" for a direct child, "(your ancestor session)" for a deeper one and "(another session)" for the rest, a parent and a sibling included, so it reads the text as information from another session and never as permission. The sender is told that only a sub session's reply can be read back, and that the owner sees any other reply in that session's own chat. An idle session is resumed and answers "Delivered". A working or waiting session is queued behind its turn and never interrupted. An archived session, and one that looks to be running in another app, are refused. The tag is our own because the CLI holds a `<cross-session-message>` that arrives on stdin (cause `no-mode-asserted`, CLI 2.1.310). Before this the tool was `send_sub_session` and reached sub sessions alone. The same change makes `list_sub_sessions` and `read_sub_session` name a session by its chip title, with an owner's rename winning. Checked with Haiku 5.5 on a test instance for a message to a sub session under the old tag, and by the fake CLI in the server tests for every session. The `<session-message>` tag was checked on a bare CLI process, and a send to a session that is not below only by the fake CLI. Not checked in Safari or on a phone.
- **Amended 2026-10-28, sending from every chat.** `send_session` is now listed to the chat of a group or a built-in section as well, so every chat GhostShell runs can message any other session, and the chat of a group or section can be sent to. The reads stay with ordinary chats. The "no session with that id" refusal now names the list tool the chat has, `list_sub_sessions` or `list_group_sessions`. See the amendment of the same date in [Give each group a session of its own](20261023-a-session-for-each-group.md).
- **Tab.** The chat's side panel gets a first tab, "Sub sessions", drawn from the list the page already loads every 15 seconds (`public/ui/subs.js`). A chat has it when the server sends `features.subStatus` and at least one row shows under it (`via` names the chat). A group's own chat always has it. The panel's name for a screen reader lists its tabs, as "Sub sessions, terminal and file".
- **Opening.** A chat with sub sessions opens the panel on the tab by itself, only while nothing is saved for the chat and the panel fits beside the chat. A phone and a narrow window wait to be asked, and a window that narrows afterwards takes the panel back instead of laying it over the chat. That opening is held in memory and is not saved as the owner's choice, and it does not take the focus from the prompt box. Once the owner has opened or closed the panel, the chat remembers it, as it remembers the terminal.
- **Header button.** A button beside the Terminal button, shown only while the tab is offered, opens the panel on the tab, switches to it from another tab, and closes the panel when the tab is already on show. The Terminal button and Ctrl+` follow the same rule for the terminal tab. The button's name carries the count and what waits, as "Sub sessions: 3, 1 waiting on you", and a mark in the awaiting colour shows while any session below, at any depth, waits on the owner. In a group's chat the count is the group's live sessions at every depth.
- **Lines.** Each line is a card with its title as a link to the session, when it last moved, a pill for its state, the owner's next step for the session (three lines at most, amended 2026-10-28), and its roll-up with "waiting on you" in the awaiting colour. Lines are grouped under Waiting on you, Working, Recent activity and Idle, each with its count in brackets, and a summary line at the top. Every session at the level shows, with no fold, and archived sessions never show, since the list the page loads leaves them out.
- **Opening a line.** A Details button on each card shows the session's latest reply in full, in a box that scrolls inside the card, and the sessions under it as cards of the same kind below the card. The reply is drawn with the markdown renderer and marked as a document, as a file in the panel is, so its code blocks have Copy and no Run. Run in another session's reply would run its command in this chat's terminal.
- **Fetching.** The page asks for the summaries of the lines it draws and no others: the top lines, and the lines inside each line that is open, in one request for each change. It splits a request over 60 ids. A line is read again when its last activity or its state changes, since what it waits on goes with its state, and a small cache keyed by id and that stamp keeps the rest. A tab that is not on show, and a closed panel, ask for nothing, and an open line does not read its reply until its tab is on show again. The reply for an open line is a second request with `detail=1` for that session alone. When a request answers, the page works out again what is stale and asks for what still is, so a line that moved while its request was out is read at once. A failed request is tried again on the next refresh of the list, not at once. The page keeps 300 summaries at most, and one that is on screen is never dropped, since asking for it again would drop another. The rules for which ids are stale and how to word a wait are in `public/ui/sub-panel-rules.js`, and node tests them.
- **Group's chat.** With `features.subStatus` the group's status moves from above the transcript to the same tab, which is the only tab of a group's chat since it has no terminal. The lines are the group's own sessions, each with its family, placed by the most urgent session in the family, and each opens as any line does. The summary line at the top is the roll-up of the group's live sessions at every depth, as "5 sessions, 1 waiting on you, 1 working", and the header button counts the same sessions. The idle sessions show as a part of their own, the archived ones are left out and never read, and the empty-state sentence stays at the bottom. The panel opens by default on a wide screen, and the header button opens it on a phone. A server without the flag keeps the status above the transcript, as it was, with its own wording ("2 need you") and no summaries asked for.
- **Folded family.** When a family is folded and the most urgent mark among the sessions under its head is more urgent than the head's own, the head's row shows that mark, and the fold button's name and tip read, for example, "4 nested sessions, 1 waiting on you". This needs only the list, so it works against the old server too. A family that is open shows each row's own mark.
- **Look.** The lines use the sidebar's marks and the group status's tokens and `.status-*` rules, with their own rules in `public/group.css` and the panel's tab look from `app.css`. Buttons and links on the tab are set to at least 44px on a touch screen, and the header buttons keep the app's centred 44px hit area, so a tap at the middle of a button reaches that button and not the one beside it. Checked in headless Chromium at 1280px and 390px, in light and dark, under the Ghost look, and with touch taps at 390px. Not checked on a real phone or in Safari, and the tab strip with three tabs at the panel's narrowest width scrolls sideways, which was not looked at.

### Consequences

- ✅ Status costs a read of a file and spends no tokens, and a parent's turn is never started by a child.
- ✅ The roll-up counts every level once, and the page and the tools count it the same way.
- ✅ The owner sees from the header, the panel or the sidebar that something below a chat waits, and what it waits for, without opening it.
- ✅ A chat's model can list and read the sessions below it and nothing else, with no card for the reads.
- ✅ A group's chat and an ordinary chat show status in one place, and a server that cannot summarise sessions looks as it did.
- ❌ The first sentence is a crude summary. A reply that opens with a greeting reads as the greeting. The tools and the group's update still show it, and a card shows it only against an old server.
- ❌ The next step is found by rules. A reply that ends on a question it answers itself reads as asking one, and an offer worded outside the rule's phrases reads as "Nothing, it's done".
- ❌ A summary is what the session last said, so a session in a long tool run says nothing new until it replies.
- ❌ What a session waits on comes from the server's live chat. A session the server has no chat for shows "waiting on you" with no detail.
- ❌ A reply written between two refreshes of the list shows up to 15 seconds late, since a line is read again when the list says the session moved.
- ❌ A request reads the end of up to 60 transcripts, up to 2 MB each. A cold cache on a large family is the slowest case, and nobody timed it.
- ❌ A reply that lies further back than 2 MB from the end of the transcript reads as no reply.
- ❌ A waiting pull request is counted by the page alone. The tools, the sidebar and the group header do not see it, so the header button can count more sessions waiting than the sidebar marks. Not checked on a real phone or in Safari.
- ❌ A sub session's transcript is read by the chat above it, through the tools. A transcript can steer the chat that reads it, so the tools' reads rest on the instructions and on every card that can act staying in place, and that includes the send card, which can now reach any session. Nothing was tried to steer a chat this way.
- ❌ A message that reaches a running session mid-turn can be ignored by the model as untrusted. It happened in 2 of about 19 Haiku 5.5 runs.
- ❌ A session that started before a restart keeps its old tool list and cannot send until its process starts again.

## Pros and Cons of the Options

### Read each session's latest reply from its transcript when asked, and roll the counts up in the page and in the tools

- ✅ No tokens, no new process and no new file kept.
- ✅ One set of rules for the page and the tools.
- ❌ The first sentence of a reply is a thin summary of the work.

### Ask a model to summarise each session

- ✅ A summary that reads the whole session.
- ❌ It spends tokens on every refresh, or goes stale between them.
- ❌ A model reading another session's transcript is steerable by it.

### Have each sub session send its status to its parent as a message

- ✅ The parent's model knows at once.
- ❌ It starts a turn in the parent for each message, and a turn can act.
- ❌ It spends tokens each time, and a parent that is idle or closed never hears.
