# Nest sessions under a parent, and follow the links Desktop records

- Status: Accepted, amended 2026-10-22, 2026-10-23, 2026-10-27, 2026-10-28, 2026-10-30 and 2026-10-31
- Deciders: Eli
- Date: 2026-10-22
- Tags: sessions, nesting, linked-sessions, layout, drag-and-drop, claude-desktop

## Context and Problem Statement

Claude Desktop records a link from a side chat to the session it was started from, and sets a flag on the side chat when the owner takes it out of the family. Desktop shows the linked sessions together. Capcom listed every session on its own, so a side chat sat apart from its parent, in another section or lower down the same one.

The owner asked to drag one session onto another to make it a child, to see children nested under their parent, to take a child out again, and to see the families Desktop already has without dragging each one. Capcom cannot write Desktop's records, and Desktop writes over them (see the [read-only list record](20261006-read-only-session-list.md)). Where does a session's parent live, where does it come from, and which side wins when Capcom and Desktop disagree?

## Decision Drivers

- Desktop's files are read only for Capcom, so a nest made in Capcom has to live in `layout.json`.
- The families Desktop has should show with no drag, and a link Desktop makes later should show too.
- Capcom's choice has to win in both directions, as the archive flag does: a session the owner nested stays nested, and one the owner took out stays out, whatever Desktop records.
- A row is also the content of a section, so a drop on a row must leave the drop on the section working.
- A family the page shows has to keep its other members, and the links among them, when one of its sessions is taken out, moved, pinned or archived, whatever chain of links lies behind it.
- Every step has to work on a phone, so a menu has to do everything a drag does.
- The walk over the links has to survive bad data: a cycle, a chain, and a parent that is archived, missing or a routine run.

## Considered Options

1. Follow Desktop's links on every refresh, and keep Capcom's nests and take-outs beside them
2. Copy Desktop's links into `layout.json` once, as the groups and pins are
3. Nest only what the owner drags in Capcom

## Decision Outcome

Chosen option: "Follow Desktop's links on every refresh, and keep Capcom's nests and take-outs beside them", because it shows Desktop's families with no drag, including the links Desktop makes later, and still lets the owner overrule Desktop in either direction. It applies the rule the archive flag already follows (see the 2026-10-18 amendment of the [layout record](20261015-own-session-layout-seeded-from-desktop.md)).

- **File.** `layout.json` gains `parents`, which maps a CLI session id to a parent's id or to null. An id nests the session under that parent. A null takes it out of the parent Desktop links it to. A session with no entry follows Desktop. A file without `parents` loads as having none and is not rewritten until something changes. An entry that is neither null nor an id is dropped as the file is read, and a `parents` that is not an object makes the file unreadable, as a bad `titles` does.
- **Desktop's links.** `lib/desktop.mjs` reads `spawnedFrom`, `forkedFromSessionId` and `lineageDetached` from each session record and keeps the link beside the fields the rows take. It follows Desktop's own rule (`parentOf`), so side chats, forks and suggested tasks all nest. A record with `lineageDetached` set has no link, and neither has one whose `spawnedFrom.userFork` is true. A side chat (`spawnedFrom.sideSession`) links to the session it was started from. When its record also names a fork (`forkedFromSessionId`) of some other session, other than the deleted parent that `spawnedFrom.deletedParent` names, the fork wins. Any other record links to the session it was forked from, or else to the one `spawnedFrom` names. A link to the record itself counts as none. Desktop names the parent by its own id, so Capcom maps it to the CLI session id through the other records and drops a link whose parent has no record or no CLI session. This is Desktop's rule with its user-links gate on, checked on Desktop 3.1623.0 only, and a NOTE beside the code says so. Capcom reads the links on every refresh, writes nothing to Desktop, and has no links when Desktop cannot be read.
- **A session's link** is Capcom's entry in `parents` when it has one, otherwise the chip it was started from, otherwise Desktop's link, otherwise none (`linkOf` in `server.mjs`). A chip links the session it started to the session that made it: `makeChips` in `lib/tools.mjs` maps each started chip's `startedId` to its `sessionId`, and a chip that is open, dismissed or missing either id makes no link. The map is built from `chips.json`, already in memory, on each refresh, and nothing new is written when a chip is started. A session started from a chip is a Capcom session, so it nests in the list instead of heading Started here. When the session that made the chip is a routine run, is missing or is not listed, it stays at the top level. Move, pin, Nest under and Move out of write `parents`, so they win over a chip as they win over Desktop. A session with a chip link counts as linked, so moving it out writes a null and hands the sessions under it on, as for any other link.
- **The walk.** `lib/families.mjs` follows each row's links upward through every row, archived ones included, and gives each row three ids. The holder is the topmost session its links reach, or the row itself. The parent is the topmost one the list shows, or null. `via` is the nearest one the list shows, or null, and orders the family. A chain stops at a null link, at an id with no row, at a routine run, which never holds children, and at a row it has passed already. A row whose chain comes back to itself is in a cycle and shows at the top level. A chain that runs into a cycle without the row in it stops at the first session of the cycle it reaches. That session is in a cycle, so it shows at the top level, and an archived session further round the cycle cannot pull the family into another place. Every parent is top level, so a family is one level deep: a grandchild shows under its topmost live ancestor, and a child that is brought back alone from an archived parent moves up to the parent's place and nests under it again when the parent comes back.
- **Place.** A family shows in its holder's place, so a child takes the holder's group or pin and its own group or pin is ignored while it is nested. Moving or pinning a parent moves its children with no extra write.
- **List.** `GET api/sessions` gives each row a `parent` (an id or null) and each top level row with children a `children` list. A child is in no other list: Pinned, the groups, Routines and the three loose lists hold top level sessions only. Children go depth first, as Desktop's do: each session that nests straight under the head, in the order of the parent's list, followed at once by the sessions that nest under it by `via`. Under a recency sort a family sorts where its best member does, so a busy child does not drop out of view under an old parent, and under the other sorts it sorts where its head does. The sorts are in [Order each list and mark each row as Claude Desktop does](20261022-list-order-and-row-marks.md). The cut at the newest 60 counts a family as one session and keeps it whole when any member was brought back from the archive. The counts in section heads and in the projects sidebar include the children.
- **Route.** `POST api/layout/nest` (`{ id, parent }`) sits behind the same sign-in and same-origin checks as the other layout routes. The server resolves `parent` to a top level session first, so a drop on a child nests under that child's parent. It writes `parents[id]` and drops the session's own pin and group, because its place is now the family's. A session that already shows under that parent is answered with the parent and nothing is written, so a repeat keeps the session's group and any link Desktop makes. A `parent` that is neither an id nor null is a 400, an unknown session or parent is a 404, an archived parent or a routine run is a 400, and so is a session nested under itself or under any session below it. That check follows the links up from the parent all the way (`chainOf` in `lib/families.mjs`), archived sessions included, because a loop through an archived session is still a loop. Each refusal is one short sentence and writes nothing. The answer is the session's `id`, `group` and `pinned` with the `parent` the list now shows.
- **Taking out.** A `parent` of null takes the session out of its parent, whether Capcom or Desktop made the link. It writes a null and the place the family showed in, so the session stays in its parent's group or in Pinned as a top level row. A parent in neither leaves the session with no group, and it shows in the loose list for the app it started in, as any such session does. The same write links each session that showed straight under it to the session it showed under (see Hidden links). A session with no link gets no write, so a link Desktop makes later is not hidden by a null written now.
- **Move, pin and archive.** `POST api/layout/move` and `pin` write a null for a session that has a link, in the same write, so a nested session that is moved or pinned leaves its parent and lands where it was sent. A session without a link gets no entry. Archiving takes the family (see Archive takes the family). It writes no link.
- **Hidden links.** A family shows one level deep, but the links behind it can run through a middle session. Kid links to Boss and Boss to Peer, and the page shows Peer with Boss and then Kid, side by side. Taking Boss out, moving it, pinning it or nesting it under another session would take Kid along, which the page did not show. So in the same write the server links each session whose `via` is the one that leaves to that session's own `via`, here Kid to Peer (`keepFamily` in `server.mjs`). The sessions further down keep their links, so each still shows under the session it showed under, where linking every member straight to the parent would flatten the family. A session handed on sorts among its new siblings by the list's sort, so it can change places with them. A head has no `via` and takes its whole family along, so nothing is relinked, and an archived session keeps its link. `lib/layout.mjs` takes those links as `relink` on `move`, `pin`, `nest` and `unnest` and writes them with the change, and a refused change writes nothing. Archiving writes no link, because the walk moves a session up by itself when the one above it is archived and it is not. That happens to Boss and Kid when Peer is archived and the owner then brings Boss back alone: Boss shows at the top level with Kid under it, and both nest under Peer again when it returns.
- **Archive takes the family.** Archiving a session archives every session below it, at any depth, in the one write that archives the session (`archive(id, { under })` in `lib/layout.mjs`). The server finds them from the index with the archived rows in it (`belowNow` in `server.mjs`), and a session below it that is archived already is skipped and keeps its own time and state. `layout.json` gains `archivedWith`, which maps each session archived this way to the session whose archive took it, so the file records the batch. A file without it loads as having none, and one where it is not an object is unreadable, as a bad `archived` is. Unarchiving works from the batch: the batch of a session is `archivedWith[id]`, or the session itself when it has none. `unarchive(id, { under })` brings back the session and each session below it that joined the same batch, drops their entries, and leaves a session the owner archived on its own earlier archived. It marks only the session asked for in `unarchived`, so a child brought back keeps whatever Desktop says of it. Unarchiving the root brings back its whole batch, below it or not (a session moved out from under it since still comes), unarchiving a session in the middle brings back what is under it from the batch, and unarchiving a child alone brings back only itself. A message sent to an archived session unarchives it the same way. A chat that is running or waiting on the owner anywhere in the family is held to the rule that held for one session. The route answers a 409 with `self` (the session itself is running) and `subs` (how many sessions below it are) when `stop` is false and writes nothing, and with `stop` true it stops every chat in the family after the write. The tool `archive_session` refuses while any of them is running or in another app, and says whether the session itself is one and how many under it are. The answer carries `subs`, the number of sessions that went or came back with the one asked for, and the page puts it in the note ("Archived “Boss” and 3 sub sessions.") and asks first, with the count, when the family has chats running. Undo unarchives the sessions that were archived, which brings back their batches and nothing archived before. The pick bar sends only the topmost of the picked sessions, so a picked session below another picked one is counted once, in its family. The tool's card says it archives the sub sessions too, the `unarchive_session` card says how many come back with the session, and the answers say how many.
- **Drag.** A row that can take the carried row carries `data-drop="nest:<id>"` and `data-drop-middle`. `public/ui/drag.js` counts such a target only in the middle half of the row's height. In the top and bottom quarters the point falls to the section around the row, so a drop between rows still moves a session into the section. The carried row, its children and routine runs take no nest. The row that would take the nest gets the sidebar accent and the ring a group gets, and says "Nest here" at its right end, left of the dot, so nothing shifts, and the section is not lit. The buttons on rows take no pointer during a drag. While a nested row is carried, its own family's list takes `nest:<parent>` without the middle-half rule, so a release anywhere in that list, on the carried row too, resolves to its current parent and sends nothing. A nested session dropped on its family's section, or on the top or bottom quarter of its parent's row, is taken out. The family's list starts where the nested rows start, so the indent to their left belongs to the section, and a nested session let go there is taken out too. One dropped on the middle of its parent's row or on a sibling sends nothing.
- **Page.** A parent's row has the fold button and nested list that a routine's earlier runs use, now shared (`.fold` and `ul.sub-rows`). Families start open, a folded family shows the mark of its most urgent session on the parent's row (see the 2026-10-23 amendment), and each browser remembers the folded ones (`folded` in local storage, holding only folded ids). A nest by drop or by menu opens the parent's family, so the row can be seen where it went. `public/app.js` shows a nest at once (`nestRow` and `unnestRow` in `public/ui/tree.js`) and puts the old list back if the server refuses, as it does for a drop on a section. A row taken out shows where the server files it: in Pinned or the group its parent is in, and otherwise in the loose list for the app the row started in. A routine run has no loose list, so it leaves the page until the server's list arrives. The rows that showed straight under a row that leaves show under the one it showed under, as the server links them, and the list places the family again. Archiving a parent takes the sessions under it too, so the whole family leaves the list at once. The search and the views treat a nested row as part of the list its parent is in.
- **Look.** Nested rows are drawn as Desktop draws them, and a routine's earlier runs share the look. A child's text starts `--nest-indent` right of its parent's, 1.25rem (18.75px) on a mouse and 1.1875rem (19px) on a touch screen, and its row ends where the parent's row ends. A line starts 0.375rem below the parent's row, with its left edge 0.75rem in from the row's left edge, which is 0.25rem right of the start of the parent's title. It runs down and turns into the middle of the last child with a `--radius-sm` corner, ending 0.375rem short of that child's title, and the rows between get no tick. On a mouse the line is 0.5px wide in the sidebar's text colour at 20%, so a 2x screen draws it one device pixel wide and a 1x screen rounds it up to one pixel. In light mode that is the grey Desktop uses, and nobody has compared dark mode with Desktop. On a touch screen it stays 1px in the sidebar's border colour. A nested row paints over the line, so a lit last child hides the end of the hook, and the line dims with a carried parent's children. The line is placed from `--row-pad`, `--row-gap` and `--nest-indent` and drawn with `--nest-line`, all tokens on `:root`, so it moves with the rows when they change size. The mouse numbers come from a 2x screenshot of Desktop's sidebar in light mode, and each lands within one device pixel of Desktop's there.
- **Keyboard.** Right on a parent opens a folded family and, with it open, moves to the first child. Left on a parent closes an open family, and left on a child moves to its parent's row. A routine's earlier runs walk the same way.
- **Menus.** A nested row's menu has Move out of “parent”. Every row's menu has Nest under, which opens a second menu of the other top level sessions in the row's section, without the row's own parent or any routine run, and the item is hidden when that list is empty. Its sub-menu has a search box that finds a session by title (see [Let groups sit under projects, and make every change from a menu](20261016-projects-above-groups.md)). A toast says `Nested “C” under “P”.` or `Moved “C” out of “P”.`, or `Not nested: <reason>` or `Not moved out: <reason>` when the server refuses. None has an Undo, as a move has none. A title can run to 120 characters and Nest under lists them, so a menu is at most 26rem wide (`min(26rem, calc(100vw - 1rem))`) and cuts a longer label with an ellipsis.

**Amended 2026-10-23, folded families.** A folded family now rolls its marks up into the parent's row. When the most urgent mark among the sessions nested under the head is more urgent than the head's own, the head's row shows that mark in its mark slot, and the fold button's name and tip say what is under it, as "4 nested sessions, 1 waiting on you" (`familyNote` in `public/ui/sub-panel-rules.js`, drawn by `Family` in `public/ui/sessions-list.js`). The order of urgency is awaiting, then error, running and unread. An open family shows each row's own mark. It reads the list the page already has, so it works against a server that cannot summarise sessions. This replaces the rule that a folded family did not roll its children's marks into the parent's row. See [Roll a session's sub session status up to every parent](20261023-roll-sub-session-status-up.md).
**Amended 2026-10-27, chips that name a group.** A chip that names a group with the `group` field of `spawn_task` no longer nests. Starting it calls `layout.move(id, group, { unlink: true })`, which writes a null into `parents` and puts the session in that group as a top level entry. A chip with no group nests as before and writes no group. See [Let a chip name the group its session opens in](20261027-chips-name-their-group.md).
**Amended 2026-10-28, a new parent for several sessions.** The owner asked to pick several sessions and make one new parent that they all nest under, in one step and with one Undo, instead of making a session and dragging each one onto it. `POST api/layout/parent` takes `{ ids, title, place }` and answers with the new id and title. `POST api/layout/parent/undo` takes `{ id }` and puts back the layout entries the first call changed, which the server kept. Both sit behind sign-in, the same-origin check and the post-body auth re-check, and the page finds support in `features.newParent`.
- **A booked parent.** The parent starts with no turn and no process. It gets a CLI id from `crypto.randomUUID`, a `started.json` entry marked `booked: true` that also holds the snapshot for Undo, and its title in `layout.json` as Capcom's own title, so the auto-titler never asks. A group's chat starts the same way. A booked entry stays in the list past 10 minutes with no transcript, and the events watch does not run the 3000-deep reindex for it. The first message uses `--session-id` and later ones `--resume`, because the runner asks `fresh()`, which is true while there is no transcript. After that first turn the session is handed to Desktop when `desktopHandoff` is on, and the startup hand-off skips a booked entry that has no transcript yet. The parent has no first message listing its children. The sub session tools read the family live, so a list written at the start would go stale as soon as a session was added or taken out, and it would cost a cold turn for every parent made. The cost is zero tokens until the owner writes in it.
- **Working folder.** Each session's folder loses a trailing `/.claude/worktrees/<name>`. When they all agree the parent uses that folder. When they differ it uses the one for the most recently active selected session. A folder that is not on disk falls through to the next candidate, and then to the home folder.
- **Place.** When every selected session shows in the same place (Pinned, one group or loose), the parent goes there. When they differ the page asks, with a select of only the places among the selection, and sends `place` as `{ group, pinned }`. The server refuses a request with differing places and no `place`.
- **Links.** A selected session whose `via` is also selected keeps its link, so a parent and its child stay as they were and the child is not lifted out. Every other selected session links straight to the new parent. A session not selected that sat under a moving one follows the nest rule and moves up with it, or stays under it, as `keepFamily` decides. The sessions nested under the parent after it was made are covered by Undo, below. A moving session's pin and group assignment are dropped, as in a nest, because it takes its place from the parent.
- **Refusals.** Each is a short sentence and writes nothing: fewer than two ids, more than 100 (checked before anything reads them, and the route reads a body of up to 64 KB so the sentence arrives and not "Send a JSON body."), an id that is not a session (404), a group's or section's chat, an archived session, a duplicate id, a title that is empty or too long, a place that names no group, and a link that would close a loop. A routine's run is allowed, as it is in nest.
- **One layout write, one Undo.** The booking is written to `started.json` first, with no snapshot, so the parent has a row from the moment its children link to it. `layout.newParent` then sets the title, the place and every link in one write to `layout.json` and keeps the entries it changed as a snapshot, and the snapshot is added to the booking. If the layout write throws, the booking is taken back out (`unbook`) and the original error is the one reported, even when the rollback fails too. A crash between the layout write and the snapshot leaves a parent with no Undo, which does no harm. A crash before the layout write leaves a parent with no children, which the owner can archive. The snapshot stays on the server, so a page cannot send one that was not made here, and the undo route takes only the id.
  Undo works for 10 minutes after the parent was made, counted from the booking's `at`, so a page left open for hours cannot replay an old snapshot over newer changes. After that it is a 409 with "It is too late to undo that. Take the sessions out by hand." Within the window it first deletes `undo` from the booking, then restores the snapshot in one layout write, skipping a group that has since been deleted. Because the snapshot is spent first, a failure part way leaves nothing to replay, and a second Undo, from another tab, is a 404. A session nested under the parent after it was made is not in the snapshot, so the same write takes it out to the parent's place: a null link, and the parent's group or Pinned. Without that it would keep a link to a parent that is gone. A parent whose chat is working, or that has a transcript, is archived and its chat is stopped, since it holds the owner's work, and the note says so. Otherwise the booking is removed and the parent leaves the list. The page shows a refusal from Undo with no Undo button, since nothing is left to retry, and keeps the button only when the server failed or could not be reached. The hand-off to Desktop after the first turn checks that the parent is still booked and not archived, so a parent taken back mid-turn is not handed over. The layout is one write in both directions, and the whole of each is two: `started.json` and `layout.json`.
- **Page.** The pick bar gets New parent beside Archive when two or more rows are picked, and a multi pick's row menu gets New parent session. The bar turns into the rename box with the title selected, built on `NameForm` with blur saving turned off so tabbing to the place select or Create does not submit. The default title is the words the titles share, or the first title and "and N more" (`parentTitle` in `public/ui/pick.js`). Enter makes the parent, Escape cancels and puts the focus back on New parent, and a change to the pick closes the form. Create stays pressable while a place is still to choose, drawn as unavailable with `aria-disabled`, and pressing it or Enter then moves the focus to the place select and makes nothing. Afterwards the pick clears, the family opens, the parent's row takes the focus and a note offers Undo. An Undo the server could not finish, or could not be reached for, keeps its button. A 404 or a 409 has nothing left to retry and shows none. A refusal shows the server's sentence and leaves the form open.

Checked: the layout method and its restore, including a session nested under the parent afterwards; every route case and refusal, including the cap on ids with a body over 10 KB; the link, folder and place rules; Undo with no messages, with a transcript, with a chat that is working, a second Undo, one after the 10 minutes, and one that fails part way; a booked parent past 30 minutes and across a restart; the first send with `--session-id`; that the owner's title wins over the first line of the transcript and the auto-titler asks nothing for a parent; and the form, Enter with no place chosen, Undo, a second Undo and a refused request in a headless Chromium shell on a desktop and a phone viewport. Not checked: the booking taken back out when the layout write throws (the layout is read first, so the test server cannot make that write fail alone), the hand-off to Desktop after the first turn and the check that skips an archived parent (the test config turns the hand-off off), a chat that is working before its transcript is written (the test CLI writes it with the first message), the loop check (a new parent cannot close a loop with data the server can make), a real Claude Desktop, and WebKit or a real phone.

**Amended 2026-10-31, a chip from a sub session starts its session beside it.** The owner asked that a session opened from a sub session go under the same parent: "When you open a sub-session from a sub-session it should go under the same parent". A sub session here is one that already shows under a parent. A chip made by a top level session nests under that session, as before.
- **Resolved once.** When the chip starts, the route reads the maker's `via` from the index with the archived rows in it and stores it on the chip as `nestUnder`. `links()` in `lib/tools.mjs` maps the started session to `nestUnder` when the chip has one, and to the maker otherwise. A maker with no `via` (top level, a group's or section's chat, a routine run, or not listed) stores nothing, and neither does a chip that names a group, which is unlinked anyway. A live link to the maker's parent was the other option. It was turned down because the new session's place would then follow every later change to the maker: taking the maker out of its parent would take the new session out too, and nesting the maker elsewhere would carry it along, which is what a child does and not a sibling. A stored id behaves as every other link does, and Move, Nest under and Move out of still overrule it.
- **Old chips.** A chip started before this change has no `nestUnder`, so its session keeps nesting under the session that made the chip.
- **Messages.** The new session and its maker show under the same parent, so they have the same `via`, and `inOwnTree` in `lib/subs.mjs` counts them as siblings. A send between them needs no card, as it would between any two siblings.
- **Started by.** The maker no longer has the new session below it, so `list_sub_sessions` would drop it. `makeChips` gains `startedBy()`, which maps each session started with `nestUnder` to the session that made its chip, and the sub session tools get it on each row. `list_sub_sessions` lists those sessions after the tree, under "Started from this session's chips, beside it:", with no roll-up line, and `read_sub_session` reads them. The sessions below one of them are not reached through it. The reply to a send says it can be read back.
- **Card.** The chip's card says `Opens beside this session, under “<parent>”`, with the group after it as before. An open chip takes the parent from the maker's `via` now, and a started one from `nestUnder`.
- **Archive.** Archiving the maker no longer takes the new session with it, because the new session is not below the maker. Archiving the parent takes both.

Checked: the chip map and `startedBy()` across a restart, the start route for a sub session's chip, a top level session's chip and a chip that names a group, the sibling place in `api/sessions`, the card lines, `list_sub_sessions` with a limit and with archived rows, `read_sub_session` refusing an unrelated session, and `inOwnTree` both ways, all in the test suite. Not checked: a chip started in the running app, and a maker whose parent is archived. In that case the new session links to the archived parent and shows at the top level until the parent comes back, while the card still names the parent.

### Consequences

- ✅ The families Desktop shows appear in Capcom with no drag, and a link Desktop records later appears on the next refresh.
- ✅ The owner nests, takes out and re-nests from a drag or from a menu, on a phone too.
- ✅ Capcom's choice wins in both directions, so a Desktop link neither undoes a nest nor brings back a family the owner took apart.
- ✅ When a nested session leaves its family or moves, the family keeps its other members, whatever chain of links lies behind them, and the sessions below that one keep their places under each other. When one is archived, the sessions below it go with it, and one Undo or one Unarchive brings the batch back.
- ✅ Nothing is written to Desktop's files.
- ✅ A session started from a chip nests under the session that made the chip, as Desktop nests the tasks it suggests, or beside it when the maker is a sub session (amended 2026-10-31). The link rests on `chips.json`, so a chip started before 2026-10-23 nests too.
- ❌ Nesting is one level deep. A session that holds others takes them along when it is nested, and a chain of links shows as one level under its topmost live session.
- ❌ A nest made in Capcom shows in Capcom only. Desktop keeps the links it has, so a session the owner took out in Capcom stays in its family in Desktop.
- ❌ An entry in `parents` stays for good. Capcom has no way yet to hand a session back to Desktop's link, so a session the owner nested or took out ignores what Desktop records for it until `parents` is edited by hand.
- ❌ A routine run cannot hold sessions, and an archived session cannot take a new child.
- ❌ Taking out, moving, pinning or nesting a nested session can add entries to `parents` for the sessions straight under it. Each entry links one of them to the session it showed under, so that the change does not move it. Archiving adds none, and adds entries to `archivedWith` instead.
- ❌ The links rest on three fields of Desktop's records, as Desktop 3.1623.0 writes them, and on its user-links gate staying on. If Desktop turns the gate off, its forks and suggested tasks stop nesting there and still nest in Capcom. After an update that moves them the families unlink until the test changes, and the nests made in Capcom stay.
- ❌ A Capcom from before this change keeps `parents` when it writes `layout.json` but does not read it, so its list shows no nesting until this version runs again. Checked by running the layout module from just before this change on a scratch file.
- ❌ A Chromium screenshot test of the line on a mouse has to set a real 2x scale with the `--force-device-scale-factor=2` flag. Under Playwright's emulated scale factor Chromium rounds the 0.5px line up to 1px and draws it two device pixels wide, where a real 2x screen draws one. WebKit's emulated scale draws one too.

## Pros and Cons of the Options

### Follow Desktop's links on every refresh, and keep Capcom's nests and take-outs beside them

- ✅ Desktop's families show with no drag, and so do the links it makes later.
- ✅ The owner's choice still wins, as the archive flag's does.
- ❌ The list reads two more fields of Desktop's internal records, which an update can move.
- ❌ Three sources decide a session's parent (Capcom's choice, the chip a session was started from, and Desktop's records), so a family in Capcom can differ from the one in Desktop.

### Copy Desktop's links into `layout.json` once, as the groups and pins are

- ✅ After the first start the list does not read Desktop's links.
- ❌ A link Desktop records after the copy never shows.
- ❌ It needs a seeding rule for links on top of the one for groups and pins, and the two layouts drift apart the way those did.

### Nest only what the owner drags in Capcom

- ✅ It is the smallest change, with nothing new read from Desktop.
- ❌ The owner nests each of Desktop's families again by hand.
